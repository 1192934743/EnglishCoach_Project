## 三、脚本清单

### 3.1 节点生成脚本

#### graph_generator.py（主生成器）

**路径**: `python_backend/scripts/graph_generator.py`

**功能**: AI 驱动的离线微场景图谱节点生成器 (v2.0 RAG 增强版)

**命令行参数**:

| 参数 | 说明 | 示例 |
|------|------|------|
| `--topic-id N` | 指定话题 ID（必需） | `python scripts/graph_generator.py --topic-id 1` |
| `--depth N` | 指定难度等级（1/2/3，默认全部） | `python scripts/graph_generator.py --topic-id 1 --depth 1` |
| `--rebuild` | 强制重建（先删除旧节点数据） | `python scripts/graph_generator.py --topic-id 1 --depth 1 --rebuild` |
| `--build-graph` | 生成后自动构建图谱 | `python scripts/graph_generator.py --topic-id 1 --depth 1 --build-graph` |

> ⚠️ **当前限制**: 不支持 `--all` 全量生成，需逐个话题执行。

### 3.2 边构建脚本

#### build_scenario_graph.py（边构建器）

**路径**: `python_backend/scripts/build_scenario_graph.py`

**功能**: 离线微场景图谱构建脚本 (v2.0 语义版)

**命令行参数**:

| 参数 | 说明 | 示例 |
|------|------|------|
| `--topic-id N` | 指定话题 ID | `python scripts/build_scenario_graph.py --topic-id 1` |
| `--depth N` | 指定难度等级 | `python scripts/build_scenario_graph.py --topic-id 1 --depth 1` |
| `--all` | 构建所有话题的所有边 | `python scripts/build_scenario_graph.py --all` |
| `--dry-run` | 预览模式，不写入数据库 | `python scripts/build_scenario_graph.py --topic-id 1 --dry-run` |
| `--rebuild` | 强制重建（删除旧边后重建） | `python scripts/build_scenario_graph.py --topic-id 1 --rebuild` |
| `--verbose` | 输出详细相似度分布 | `python scripts/build_scenario_graph.py --topic-id 1 --verbose` |
| `--build-cross-topic` | 构建跨话题边 | `python scripts/build_scenario_graph.py --build-cross-topic` |

**算法说明**:
1. 遍历同 Topic + 同 Depth 下所有 MicroScenario
2. 加载每个 MicroScenario 绑定的 ScenarioConstraint
3. 从 DB 加载场景向量，构建 ScenarioVectorIndex
4. 垂直连线（Step N -> Step N+1）：相似度 >= 0.65 时建立连接
5. 横向迁移（同 Step 内）：当 0.85 <= similarity <= 0.92 时建立双向迁移边
6. 输出图谱健康度报告

### 6.2 批量生成流程（推荐方式）

> ⚠️ **重要**：请勿使用 Bash 循环硬编码话题 ID，这种方式极其脆弱且无法感知数据库变化。

**推荐做法**：使用 Python 一键调度脚本 `generate_full_graph.py`

```bash
# 一键生成所有话题的所有图谱
python scripts/generate_full_graph.py --all

# 增量模式：只为缺失场景的话题生成
python scripts/generate_full_graph.py --missing-only

# 预览模式（不实际调用 API）
python scripts/generate_full_graph.py --all --dry-run

# 强制重建
python scripts/generate_full_graph.py --all --rebuild
```

**调度器内部逻辑**：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    generate_full_graph.py 调度流程                          │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  1. 初始化                                                              │
│     └── 从 DB 查询: SELECT id FROM topics ORDER BY id                    │
│                                                                         │
│  2. 节点生成阶段（Python 循环，动态感知话题）                              │
│     └── for topic in topics:                                           │
│         └── for depth in [1, 2, 3]:                                   │
│             ├── 检查是否已存在（幂等）                                    │
│             ├── 调用 graph_generator 逻辑                                │
│             ├── [主动限流] 每请求间隔 1-2 秒                              │
│             └── 进度日志：已完成 N/M                                    │
│                                                                         │
│  3. 边构建阶段（全局视角，一次性完成）                                    │
│     └── build_scenario_graph.py --all --build-cross-topic               │
│                                                                         │
│  4. 健康检查                                                            │
│     └── 孤立节点检测 + 统计报告                                          │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────────┘
```

> 💡 **为什么用 Python 调度？**
> - 数据库 ID 不固定，Python 直接查询确保动态感知
> - 统一的限流、日志、错误处理
> - 可在最后统一触发跨话题连线（需要所有节点已生成）

## 八、容错与限流机制

### 8.1 API 主动限流（Proactive Rate Limiting）

> ⚠️ **重要**：Gemini API 有 RPM（每分钟请求数）和 TPM（每分钟 Token 数）限制。全速并发请求会导致 429 Too Many Requests 错误，被封禁后重试也会继续失败。

**实现方案**：

| 方案 | 适用场景 | 实现方式 |
|------|----------|----------|
| Semaphore 信号量 | asyncio 并发控制 | `asyncio.Semaphore(max_concurrent)` |
| 固定延迟 | 简单限流 | `asyncio.sleep(1.5)` 每请求间隔 |
| Token Bucket | 精细控制 | `aiohttp-Limiter` 或手动实现 |
| 指数退避 + jitter | 被动重试 | tenacity + random jitter |

**推荐配置**（Gemini 2.5 Pro）：

```python
# 方案 A：Semaphore 控制并发
MAX_CONCURRENT = 3  # 同时最多 3 个请求
semaphore = asyncio.Semaphore(MAX_CONCURRENT)

# 方案 B：固定间隔（简单可靠）
MIN_REQUEST_INTERVAL = 1.5  # 秒，最少间隔
await asyncio.sleep(MIN_REQUEST_INTERVAL)
```

**为什么不只用被动重试？**

| 方案 | 429 发生时 | 结果 |
|------|-----------|------|
| 仅被动重试 | 触发限流 → 报错 → 等待 → 重试 → 再次触发 | 效率低，可能陷入循环 |
| 主动限流 + 重试 | 限流前就控制频率 → 偶发 429 → 重试 | 平滑稳定 |

### 8.2 错误重试机制

| 机制 | 实现方式 | 说明 |
|------|----------|------|
| API 重试 | tenacity 库 + 指数退避 | 网络抖动自动恢复 |
| 断点续传 | Depth 级别检查 | 跳过已完成的，避免重复扣费 |
| 幂等保护 | `--rebuild` 显式重建 | 默认只新增，不覆盖 |
| 进度保存 | 每个 Depth 完成即落库 | Ctrl+C 后可安全重启 |

### 8.3 进度反馈

> 💡 用户运行脚本时，最怕的就是"卡住了吗？"——需要实时进度反馈。

## 十、深度等级定义

### 10.1 Depth 1 - Foundation (Core Survival Phrases)

- **目标**: 用最简单的词汇完成核心交际功能
- **词汇**: 高频基础词汇，短语优先（如 I want, a coffee, how much）
- **约束**: 仅生成 2-3 个最基础的词汇
- **示例**: Constraints: ["I want", "coffee", "large"]

### 10.2 Depth 2 - Intermediate (Politeness & Detail Modifiers)

- **目标**: 在基础功能上添加细节修饰词和礼貌表达
- **词汇**: 高级复合词，完整简单句（如 I would like, instead of, with oat milk）
- **约束**: 生成 3-4 个约束，必须包含至少一个礼貌表达或修饰词
- **示例**: Constraints: ["I would like", "a latte", "with oat milk", "please"]

### 10.3 Depth 3 - Advanced (Native Expressions & Complex Sentences)

- **目标**: 使用母语者的惯用语、间接请求或复杂从句
- **词汇**: 高级词汇、虚拟语气、复杂句（如 I was wondering if, would it be possible to）
- **约束**: 生成 4-5 个约束，必须包含高级交际模式
- **示例**: Constraints: ["I was wondering if", "could possibly make it", "decaf", "extra shot"]

## 十一、模型使用规范

| 场景 | 使用模型 | 说明 |
|------|----------|------|
| Topic 生成（文本） | DeepSeek | 成本低，效果足够 |
| MicroScenario 生成（文本） | Gemini 2.5 Pro | 质量更高 |
| **Embedding 向量生成** | **Gemini `models/embedding-001`** | **硬性要求，不可替换** |
| Scene Rules 优化 | Gemini | 质量要求高 |

> ⚠️ **警告**: Embedding 向量是图谱连线的命根子，必须使用 Gemini `models/embedding-001`。跨话题边的相似度计算完全依赖 embedding 质量，混用其他模型会导致边构建结果不可靠。

## 十二、相似度阈值

| 边类型 | 阈值 | 说明 |
|--------|------|------|
| 垂直连线（VERTICAL） | sim >= 0.65 | 最低相似度，防止串线 |
| 横向迁移下限（HORIZONTAL_MIN） | sim >= 0.85 | 最低横向迁移阈值 |
| 横向迁移上限（HORIZONTAL_MAX） | sim <= 0.92 | 避免过相似 |
| 跨话题边（CROSS_TOPIC） | sim >= 0.85 | 跨话题入口节点 |
